### [CRITICAL] Next.js 16.2.4 — Multiple CVEs (DoS, SSRF, XSS, RCE, Cache Poisoning, Middleware Bypass)
**File:** `package.json`
**Detail:** The installed Next.js version (16.2.4) is flagged with ~30+ advisories including several rated critical/high: unauthenticated RCE in Image Optimization and `use cache` functions, SSRF in Server Actions, middleware/proxy bypass via segment-prefetch routes and dynamic route injection, cache poisoning of SSG/ISR pages, XSS in `beforeInteractive` scripts, and multiple DoS vectors (Server Actions, Image Optimization API, connection exhaustion). The app is deployed on Vercel, which mitigates some self-hosted RCE vectors, but middleware bypass and cache poisoning are still relevant.
**Status:** Needs manual review — upgrade Next.js
**Recommendation:** Upgrade to the latest stable Next.js 16.x patch. Run `npm update next` and check the Next.js changelog for any breaking changes. Vercel's managed infrastructure reduces exposure for some of these (especially self-hosted RCE), but do not delay upgrading.

### [HIGH] Custom regex HTML sanitizer used for dangerouslySetInnerHTML
**File:** `src/lib/sanitize.ts:5`, `src/components/admin/work-order-template-editor.tsx:216`, `src/components/admin/contract-template-editor.tsx:176,322`
**Detail:** `sanitizeHTML()` uses a hand-rolled regex chain to strip dangerous HTML. Regex-based sanitization is well-known to be bypassable via nested tags, attribute encoding tricks, case mutations, HTML parser quirks, and other techniques. While these components are admin-only, an admin could inadvertently save malicious content that is then rendered by other users (e.g., teachers viewing work orders/contracts). The function also does not strip `<svg>`, `<math>`, or `<details>` attack vectors.
**Status:** Needs manual review — replace with battle-tested sanitizer
**Recommendation:** Replace `sanitizeHTML` with DOMPurify (browser-side: `import DOMPurify from 'dompurify'`) or `sanitize-html` (server-safe). For server-side use in `students/[studentId]/route.ts`, use `sanitize-html`. Configure an allowlist of permitted tags rather than a denylist.

### [HIGH] @tiptap/core — Prototype Pollution XSS + ReDoS
**File:** `package.json` (transitive via tiptap editor components)
**Detail:** `@tiptap/core <=3.30.4` has two advisories: (1) `mergeAttributes()` can turn an `__proto__` key into inherited executable DOM attributes, enabling XSS via prototype pollution; (2) quadratic ReDoS in Markdown attribute parsing. The tiptap editor is used in admin-facing template editors.
**Status:** Needs manual review — upgrade @tiptap packages
**Recommendation:** Run `npm update @tiptap/core @tiptap/react @tiptap/extensions` (and all `@tiptap/extension-*` packages) to >=3.30.5. Verify the tiptap editor still functions after the upgrade.

### [HIGH] DOMPurify (transitive) — Multiple XSS bypass vectors in IN_PLACE mode
**File:** `package.json` (transitive dependency, likely via @tiptap)
**Detail:** Multiple DOMPurify CVEs in the installed version affect `IN_PLACE` sanitization mode: realm-bound `instanceof` checks leave executable markup, clobbered root element attributes survive sanitization, hook mutation pollutes `DEFAULT_ALLOWED_TAGS`, SAFE_FOR_TEMPLATES bypass inside `<template>` content, and others. Impact is limited here since the app's own `sanitizeHTML()` does not use DOMPurify — this affects tiptap's internal HTML handling only.
**Status:** Needs manual review — resolved by upgrading @tiptap (which will pull a patched DOMPurify)
**Recommendation:** Upgrade @tiptap as above; DOMPurify will be updated as part of that dependency chain.

### [MEDIUM] Project documents upload — no file type or size validation
**File:** `src/app/api/admin/projects/[id]/documents/route.ts:63-100`
**Detail:** The file upload branch of this admin-only route accepts any file type and any file size. While admin-only auth is enforced, there is no guard against uploading malware, executables, or multi-GB files. Compare to `upload-invoices/route.ts` which validates `file.type !== 'application/pdf'` and `file.size > 20MB`.
**Status:** Needs manual review (admin-only, low blast radius, but inconsistent with other upload routes)
**Recommendation:** Add file size limit (e.g. 50MB) and optionally restrict to common document types (pdf, docx, xlsx, png, jpg, zip). Example addition after `if (!file)` check:
```ts
if (file.size > 50 * 1024 * 1024) {
  return NextResponse.json({ error: "File too large (max 50MB)" }, { status: 400 });
}
```

## All Clear (Checked and Confirmed Safe)

- **Hardcoded secrets**: None found in `.ts`/`.tsx` source files. All credentials use `process.env.*`.
- **Admin API routes**: All `/api/admin/*` routes check `supabase.auth.getUser()` and verify `role === 'admin'`.
- **Portal API routes**: All `/api/portal/*` routes check `supabase.auth.getUser()`.
- **Messages + Notifications routes**: Both authenticate via `supabase.auth.getUser()`.
- **DATEV OAuth routes**: Rate-limited and require admin authentication.
- **Webhook signature verification**: Monday, Squarespace, and Squarespace-claim webhooks all require a bearer token and return 401 without it. Production mode requires the env var to be set.
- **Cron secret verification**: All three cron routes validate `Bearer CRON_SECRET`. Health check and check-expiry verified.
- **XSS — dangerouslySetInnerHTML**: Three usages found, all call `sanitizeHTML()`. However, the sanitizer itself is a custom regex implementation — see HIGH issue above.
- **SQL injection**: No raw SQL string interpolation found. All Supabase queries use parameterized builder methods. The `.or()` calls with UUIDs from authenticated session context are acceptable (PostgREST filter syntax, not raw SQL).
- **File uploads (invoices)**: Type-checked (`application/pdf` only) and size-limited (20MB). ✅
- **File uploads (brochure)**: Type-checked (`application/pdf` only). ✅
- **File uploads (extract)**: Type-checked (`application/pdf` only). ✅
- **School token routes**: Token validated against DB on every request. Rate-limited (3 req/min/IP).
