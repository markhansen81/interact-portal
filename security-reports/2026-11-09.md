### [CRITICAL] Next.js 16.2.4 — Multiple CVEs (not fixed since 2026-11-05)
**File:** `package.json`
**Detail:** Next.js 16.2.4 has 33 individual advisories covering:

- RCE in `next/og` ImageResponse and `use cache` functions returning typed arrays
- Multiple SSRF via WebSocket upgrades, Server Actions, rewrites

- Cache poisoning (SSG/ISR pages, RSC cache-busting, response body confusion)

- Unauthenticated disclosure of internal Server Function endpoints
- CSP nonce XSS in App Router; XSS in `beforeInteractive` scripts
- Information disclosure in dev server MCP endpoint and metadata image routes

**Status:** Needs manual review — **HIGHEST PRIORITY** (unchanged from previous report)
**Recommendation:** Update Next.js to the latest stable release. Run `npm audit fix` or manually bump `next` in `package.json` and test thoroughly. The Image Optimization RCE is especially severe if the `/api/image` endpoint is reachable from the internet.

### [HIGH] Custom regex HTML sanitizer used in `dangerouslySetInnerHTML` (not fixed)
**File:** `src/lib/sanitize.ts`, `src/components/admin/work-order-template-editor.tsx:216`, `src/components/admin/contract-template-editor.tsx:176,322`
**Detail:** The app uses a homegrown regex-based `sanitizeHTML()` function instead of a battle-tested library. Regex HTML sanitizers are routinely bypassed via nested/malformed tags, CSS expressions, SVG vectors, mutation XSS, and attribute injection. The function is applied to admin-facing template previews — lower risk than user-facing but not zero risk, especially if template content is editable.

**Status:** Needs manual review
**Recommendation:** Replace `sanitizeHTML()` with `sanitize-html` npm package or DOMPurify (server-side via jsdom). Since this is admin-only, the blast radius is limited, but the dependency on a custom sanitizer is a code smell.

### [MEDIUM] Unauthenticated GET `/api/admin/form-content` (not fixed)
**File:** `src/app/api/admin/form-content/route.ts:4`
**Detail:** The GET handler returns all rows from the `form_content` table without any authentication check. Any unauthenticated request can retrieve all form content. The PATCH handler correctly requires admin auth. The `/api/admin/` prefix is misleading.

**Status:** Needs manual review
**Recommendation:** Either (a) confirm intentional and move route to `/api/public/form-content` with a comment explaining the deliberate lack of auth, or (b) add auth if the data should not be public. This was flagged in the 2026-11-05 report and remains unresolved.

### [MEDIUM] Admin project document upload — no file size or MIME type validation
**File:** `src/app/api/admin/projects/[id]/documents/route.ts:62–82`
**Detail:** The file upload code path reads the file from FormData and uploads it to Supabase storage without validating the file size or MIME type. By contrast, `src/app/api/admin/upload-invoices/route.ts` enforces a 20 MB size limit and type checks. An admin uploading a very large or unexpected file type could exhaust storage quota or cause unexpected behaviour downstream.

**Status:** Needs manual review (admin-only route — lower risk, but inconsistent with other upload routes)
**Recommendation:** Add a file size limit (e.g. 20 MB, matching the invoice upload route) and optionally a MIME type allowlist (PDF, images, Word). Example:
```ts
if (file.size > 20 * 1024 * 1024) {
  return NextResponse.json({ error: "File too large (max 20MB)" }, { status: 400 });
}
```

## All Clear

The following were checked and confirmed safe:

- **Hardcoded secrets**: No `sk_`, `eyJ`, `api_key =`, `password =`, or `secret =` literals found in `.ts`/`.tsx` source files
- **SQL injection**: No raw SQL string interpolation found — all queries use the Supabase ORM with parameterized inputs
- **Missing auth on admin routes**: All `/api/admin/*` routes check auth via `supabase.auth.getUser()` + role check; the one exception (`form-content` GET) is documented above
- **Missing auth on portal routes**: All `/api/portal/*` routes check `supabase.auth.getUser()` and return 401 if unauthenticated
- **Cron route auth**: All 3 cron routes (`check-expiry`, `update-levels`, `health-check`) verify `CRON_SECRET` before executing
- **Webhook auth**: Monday.com (all 3 routes) and Squarespace (both routes) validate bearer tokens; Monday additionally handles challenge verification
- **XSS via dangerouslySetInnerHTML**: All 3 usages wrap content with `sanitizeHTML()` (noted above as HIGH due to custom regex, but not unprotected)
- **School portal (OTP + magic link)**: OTP is compared server-side with timing-safe lookup; session key is `randomBytes(32)`, stored as httpOnly cookie; email enumeration is avoided
- **DATEV auth**: Admin role check + rate limiting (3 req/min per IP) confirmed
- **School token-based routes**: Token validated against `teacher_token` in DB; email must match project's `teacher_email` (case-insensitive); no enumeration possible
- **Messages/notifications**: Both routes check `supabase.auth.getUser()` and enforce user-scoped data access
- **Intentionally public routes confirmed**: `lead-form`, `health`, `school/magic-link/*`, `school/otp/*` — no auth required and appropriate
