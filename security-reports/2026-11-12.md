## Issues Found

### [CRITICAL] Next.js 16.2.4 has 33+ unpatched CVEs
**File:** `package.json`
**Detail:** The installed version of Next.js (16.2.4) is flagged with 33+ CVEs including unauthenticated Remote Code Execution (image optimization API with AVIF/SVG), Server-Side Request Forgery in Server Actions and rewrites, multiple middleware/proxy bypass vulnerabilities, cache poisoning in SSG/ISR pages, and XSS via CSP nonces. This is the most critical finding.
**Status:** Needs manual review
**Recommendation:** Run `npm audit fix --force` after testing, or manually upgrade Next.js to the latest patched version. Review the Next.js changelog for breaking changes before upgrading. Priority: address before the next production deployment.

### [HIGH] @tiptap/react ^3.22.5 has prototype pollution XSS + ReDoS
**File:** `package.json`
**Detail:** `@tiptap/core` (a dependency of `@tiptap/react`) has two high-severity CVEs:
- **GHSA-cp6q-959q-f8rh**: `mergeAttributes()` can turn an `__proto__` key into inherited executable DOM attributes — prototype pollution leading to XSS (affects >=2.0.0-alpha.0 <3.30.4).
- **GHSA-j95f-988m-3j2f**: Quadratic ReDoS in block and inline Markdown attribute parsing (affects >=3.7.0 <3.30.5).
The editor is used in admin-only components (`work-order-template-editor.tsx`, `contract-template-editor.tsx`), so XSS exposure is limited to authenticated admins, but prototype pollution is still a concern.
**Status:** Needs manual review
**Recommendation:** Upgrade `@tiptap/react` to `^3.30.5` or later in `package.json`.

### [HIGH] DOMPurify transitive dependency has multiple XSS bypass CVEs
**File:** `package.json` (transitive)
**Detail:** `dompurify` is a transitive dependency flagged with 13+ high-severity CVEs, mostly around `IN_PLACE` mode bypasses, prototype pollution via `setConfig()`, and Trusted Types policy issues. The project does **not** directly import DOMPurify — it uses a custom regex-based `sanitizeHTML()` function (`src/lib/sanitize.ts`) instead. This custom sanitizer is not library-level sanitization and may be bypassable via encoding tricks or unusual HTML constructs. DOMPurify CVEs may be in a dependency that never calls it in vulnerable modes.
**Status:** Needs manual review
**Recommendation:** (1) Identify which package imports DOMPurify transitively and whether it's called with `IN_PLACE`. (2) Consider replacing the custom `sanitizeHTML` regex in `src/lib/sanitize.ts` with a proper server-side sanitizer (e.g. `sanitize-html` npm package or `isomorphic-dompurify`) for defence-in-depth — the custom regex could be bypassed.

### [MEDIUM] Admin documents upload accepted any file type (Auto-fixed)
**File:** `src/app/api/admin/projects/[id]/documents/route.ts:67`
**Detail:** The file upload path in the admin project documents route accepted any MIME type with no size limit. An authenticated admin could upload arbitrary file types (e.g. HTML, SVG, executable) to Supabase storage, which could lead to stored XSS if storage files are served with permissive content-type headers.
**Status:** Auto-fixed — added 25MB size limit and allowlist of safe MIME types (PDF, images, Word, Excel, plain text).
**Recommendation:** Confirm Supabase storage bucket policy also sets content-disposition: attachment or restricts served content-types. Verify the fix doesn't break existing upload flows.

### [MEDIUM] Custom regex HTML sanitizer in `src/lib/sanitize.ts`
**File:** `src/lib/sanitize.ts`
**Detail:** The project uses a hand-rolled regex-based HTML sanitizer instead of an established library. Regex sanitizers are notoriously incomplete — they can be bypassed with uncommon attribute quoting, nested elements, or Unicode encoding tricks. The function is used in `dangerouslySetInnerHTML` rendering of admin-editable templates and in a school portal API route.
**Status:** Needs manual review
**Recommendation:** Replace with `isomorphic-dompurify` (server + client safe) or `sanitize-html` (server-safe). Priority is medium because usage is in admin-authenticated UI and one school-portal endpoint, not public-facing.

### [LOW] `school_otp_sessions` table has no RLS
**File:** `supabase/migrations/20261101120000_school_otp_sessions.sql`
**Detail:** The `school_otp_sessions` table was created without enabling Row Level Security. OTP codes are stored in plain text (described as short-lived 15-min codes). The table is only accessed server-side via the admin client (service_role), so there is no immediate risk from application code, but a compromised Supabase connection with anon key could read active OTP codes.
**Status:** Needs manual review
**Recommendation:** Add a migration to `ALTER TABLE school_otp_sessions ENABLE ROW LEVEL SECURITY` and add a service-role-only policy. Also consider hashing OTP codes at rest (bcrypt/SHA-256) since they are short-lived credentials.
