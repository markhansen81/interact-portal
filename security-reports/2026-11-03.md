### [MEDIUM] Homegrown Regex HTML Sanitizer
**File:** `src/lib/sanitize.ts`
**Detail:** The `sanitizeHTML()` function uses regex patterns instead of a battle-tested library. Regex-based HTML sanitizers are routinely bypassed with techniques like nested tags, unusual encoding, SVG/MathML injection, and HTML parser inconsistencies. Current patterns may miss vectors like `<img src=x onerror=...>` or exotic tag variations.
**Status:** Needs manual review
**Recommendation:** Replace with DOMPurify (server-side via jsdom) or `sanitize-html` npm package. Since these templates are currently only used by admins (in `work-order-template-editor.tsx` and `contract-template-editor.tsx`), risk is reduced but still present if an admin account is compromised.

### [MEDIUM — AUTO-FIXED] OTP Generation Uses Math.random()
**File:** `src/app/api/school/otp/send/route.ts:6`
**Detail:** `generateOTP()` used `Math.floor(100000 + Math.random() * 900000)` — `Math.random()` is not cryptographically secure. A predictable PRNG seed could allow an attacker to predict OTP values.
**Status:** ✅ Auto-fixed — replaced with `crypto.randomInt(100000, 1000000)`
**Recommendation:** No further action needed. Auto-fix applied and committed.

### [MEDIUM — AUTO-FIXED] OTP Endpoints Missing Rate Limiting
**File:** `src/app/api/school/otp/send/route.ts`, `src/app/api/school/otp/verify/route.ts`
**Detail:** Neither OTP send nor verify endpoint had rate limiting. Without it:
- `/send`: Attacker could spam OTP emails to any teacher in the system
- `/verify`: Attacker has the full 15-minute OTP window to attempt brute force against a 6-digit code (10^6 permutations). Even at 10 req/s that's a theoretical 27-hour window but with distributed load the risk is real.
**Status:** ✅ Auto-fixed — added `rateLimit(ip, 5, 60_000)` to send, `rateLimit(ip, 10, 60_000)` to verify
**Recommendation:** No further action. Note: in-memory rate limiter is per-serverless-instance; for stronger guarantees, consider moving rate limit state to Redis/Upstash.

### [LOW] Monday Webhook Auth: Bearer Token vs HMAC
**File:** `src/app/api/webhooks/monday/route.ts`, `src/app/api/webhooks/monday/projects/route.ts`
**Detail:** Webhook authentication uses a simple `Authorization: <token>` string comparison rather than HMAC signature verification. If the secret leaks (logs, env dump), any party can replay webhook payloads. Monday.com does support HMAC signing; the current approach is functional but weaker.
**Status:** Needs manual review
**Recommendation:** If Monday.com supports HMAC webhook signatures for your plan, switch to verifying `x-monday-signature` with HMAC-SHA256. Otherwise ensure `MONDAY_WEBHOOK_SECRET` is rotated periodically and not logged.

---

### [INFO] Squarespace Webhook — No Native Signature Verification
**File:** `src/app/api/webhooks/squarespace/route.ts`
**Detail:** Squarespace webhook events arrive via Zapier with a bearer token (`SQUARESPACE_WEBHOOK_SECRET`). Squarespace's own API does not provide HMAC signing for webhook delivery via Zapier. Current approach (bearer token) is correct for this integration pattern.
**Status:** All clear — intentional design, no action needed.
